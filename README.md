# Snowflake Agent Research

Empirical research on Snowflake Cortex Agent performance — table scaling limits, view routing, model sensitivity, and hallucination rates at enterprise scale.

## Problem Statement

AI agents that answer natural language questions over structured data (text-to-SQL) are being adopted by large enterprises. But nobody has published controlled experiments answering: **at what point do these agents break down as schema complexity increases?**

This project builds a rigorous evaluation framework and runs 5 experiments that quantify exactly where accuracy degrades, latency explodes, and — critically — where the agent starts fabricating answers with confidence.

## Summary of Findings

| Finding | Impact |
|---------|--------|
| Accuracy drops ~13pts when a semantic view exceeds 10-15 tables | Architecture constraint for production |
| Extra views attached to one agent do NOT hurt routing | Safe to scale horizontally |
| More tables makes the agent fabricate answers 56% of the time on unanswerable questions | Critical trust problem |
| Abstention instructions reduce fabrication by ~7pts but don't solve it | Instructions alone are insufficient |
| T20 agents are 3.6x slower per question than T5 (p50) | Latency penalty compounds the accuracy cliff |
| A routing guide improves ambiguous questions +7pts without regression | Low-cost optimization |
| Budget models (GPT-mini) degrade with more views; premium models don't | Model selection is architecture-dependent |

---

## How Cortex Agents Work

A Cortex Agent is a SQL-defined AI interface that:
1. Reads a **semantic view** (metadata describing tables, columns, relationships, and business terms)
2. Uses an **orchestration model** (Claude Sonnet, Haiku, GPT-mini, etc.) to generate SQL from natural language
3. Executes the SQL against the warehouse
4. Returns results in natural language

The research question: **at what point does this process break down?**

## Evaluation Framework

Automated pipeline for statistically rigorous testing:

```
Question Dataset (with ground-truth SQL answers)
        │
        ▼
┌─────────────────────────────────────┐
│  YAML Eval Config                   │  ← Points to agent + dataset
└─────────────────────────────────────┘
        │
        ▼
┌─────────────────────────────────────┐
│  EXECUTE_AI_EVALUATION              │  ← Sends questions, captures responses
└─────────────────────────────────────┘
        │
        ▼
┌─────────────────────────────────────┐
│  LLM Judge (llama3.1-70b)           │  ← Scores 0-1 against ground truth
└─────────────────────────────────────┘
        │
        ▼
┌─────────────────────────────────────┐
│  Statistical Analysis               │  ← 5 runs per condition, mean ± stddev
└─────────────────────────────────────┘
```

**Key design decisions:**
- Every condition run **5 times** with results reported as mean ± standard deviation
- Ground truth generated by **executing reference SQL** against actual data (not hand-written)
- Same questions across tiers; only distractor count varies
- Failed/empty runs identified and excluded from analysis

## Experiments

### Experiment 1: Table Scaling (`q1/`)

**Question:** Does adding more tables to a single semantic view degrade answer quality?

**Design:** 27 questions (all answerable from 5 core tables) asked to agents with 5, 10, 20, or 40 tables. Extra tables are pure distractors.

| Model | T5 (5 tables) | T10 (10 tables) | T20 (20 tables) | Drop T10→T20 |
|-------|:---:|:---:|:---:|:---:|
| Claude Sonnet | 89.2% ±0.6 | 90.6% ±2.4 | 76.5% ±2.5 | **-14.1 pts** |
| Claude Haiku | 85.0% ±1.0 | 84.0% ±1.5 | 73.6% ±2.9 | **-10.4 pts** |
| GPT-mini | 85.9% ±1.7 | 82.7% ±7.5 | 71.6% ±6.0 | **-11.1 pts** |

**Latency impact:**

| Tier | p50 | p95 | Multiplier |
|------|-----|-----|-----------|
| T5 | 14.9s | 34.8s | 1x |
| T20 | 53.2s | 256.7s | 3.6x (p50), 7.4x (p95) |

**Token cost:** T20 agents consume 16-43% more input tokens than T5 on identical questions.

**Conclusion:** The cliff is at 10-20 tables. Beyond 15 tables, you pay more, wait longer, and get worse answers.

---

### Experiment 2: View Routing (`q2/`)

**Question:** Does attaching more semantic views to one agent degrade routing accuracy?

**Design:** 12 business domains (Sales, Marketing, CRM, Finance, HR, Payroll, Supply Chain, etc.) with separate semantic views. Same 19 questions tested on agents with 4 views vs 12 views.

| Model | V4 (4 views) | V12 (12 views) | Difference |
|-------|:---:|:---:|:---:|
| Claude Sonnet | 84.9% ±2.0 | 85.3% ±2.4 | No degradation |
| Claude Haiku | 81.4% ±2.7 | 82.1% ±1.5 | No degradation |
| GPT-mini | 57.2% ±5.8 | 52.6% ±8.6 | -4.6pts (degrades) |

**Routing guide optimization (plain-English instructions for disambiguation):**

| Question Category | Baseline | With Guide | Change |
|-------------------|:---:|:---:|:---:|
| Ambiguous questions | 66.0% | 73.4% | **+7.3 pts** |
| Cross-view questions | 69.9% | 74.6% | **+4.7 pts** |
| Stress test | 74.7% | 80.6% | **+6.0 pts** |

**Conclusion:** Extra views are safe for premium models. A routing guide is a free +7pt improvement.

### Experiment 3: Model Sensitivity (`q3/`)

**Question:** Which LLMs work as Cortex Agent orchestrators?

| Model | Works | Relative Cost | Notes |
|-------|:---:|:---:|-------|
| Claude Sonnet | Yes | 1x | Best cost/performance ratio |
| Claude Haiku | Yes | 0.33x | Slight accuracy loss, higher latency penalty at scale |
| GPT-mini | Yes | 0.13x | Can't route effectively with many views, high variance |
| Claude Opus | Yes | 5x | No proven benefit over Sonnet |
| DeepSeek-R1 | No | — | Creates agent but never executes queries |
| Llama 3.1 70B | No | — | Creates agent but never executes queries |

**Conclusion:** Use Sonnet for production. Haiku for cost-sensitive workloads with <15 tables. Open-source models are not yet supported.

---

### Experiment 4: Architecture Comparison (`q4/`)

**Question:** Should you keep 20 tables in one view or split into focused topic views?

**Design:** Same 20 tables packaged as (a) one monolithic view or (b) four topic views with routing. 50 questions tagged by scope.

| Question Type | One Big View | Four Topic Views | Winner |
|---------------|:---:|:---:|:---:|
| Single-topic (27 questions) | 67.8% | 77.8% | **Topic views +10pts** |
| Multi-topic (23 questions) | 72.5% | 60.9% | **Big view +12pts** |
| Overall | ~72% | ~71% | Tie |

**Conclusion:** Architecture depends on query patterns. Focused workloads benefit from split views; cross-domain workloads need unified views.

---

### Experiment 5: Trust & Hallucination (`q5/`)

**Question:** How often does the agent fabricate numbers on unanswerable questions? Does it get worse with more tables?

**Design:** 20 intentionally unanswerable questions across 4 categories: out-of-scope metrics, non-existent entities, ambiguous concepts, and tier-gated data.

| Tier | Baseline Refusal | With Abstention Instruction | Fabrication Rate |
|------|:---:|:---:|:---:|
| T5 (5 tables) | 70% | 73% | **30%** |
| T10 (10 tables) | 47% | 54% | **53%** |
| T20 (20 tables) | 44% | 51% | **56%** |

**Key insight:** More tables = more fabrication. At T5, the agent clearly sees data isn't available and refuses correctly. At T20, it finds creative (wrong) ways to fabricate an answer 56% of the time. Even explicit "don't fabricate" instructions only help +7pts.

**For enterprise deployments, this is the most critical finding.** A wrong refusal is annoying. A fabricated number presented with confidence is dangerous.

---

## Actionable Recommendations

1. **Keep semantic views under 10-15 tables.** Beyond that, accuracy drops ~13pts and latency increases 3-7x.
2. **Scale horizontally with multiple views.** Adding views to one agent is safe (for Claude models).
3. **Write routing instructions.** A plain-English guide improves ambiguous questions +7pts with zero downside.
4. **Don't use budget models for multi-view routing.** GPT-mini can't effectively choose between tools.
5. **Trust is the bigger problem than accuracy.** At 20 tables, fabrication rate (56%) exceeds the accuracy cliff. Guardrails beyond instructions are required.
6. **Match architecture to query patterns.** Single-domain workloads → split views. Cross-domain → unified views.

## Dataset Design

**Single-domain (Experiments 1, 3, 4, 5):**
- 1 fact table: 100,000 transactions ($10-$500 each)
- Nested dimension tiers: T5 → T10 → T20 → T40 (each superset of previous)
- Generated with `UNIFORM(min, max, RANDOM(seed))` using unique seeds per column for independence

**Multi-domain (Experiment 2):**
- 5 shared dimensions (customer, product, date, geography, employee)
- 12 independent fact tables across business domains
- 100,000 rows per fact table

## Methodology Notes

- **Data integrity fix:** Original data generator had a FK bug (all columns used same random seed). Fixed in v4 — all results use corrected data with verified multi-dimensional independence.
- **Platform limitations discovered:** `logical_consistency` metric broken; generated SQL not exposed in eval output; dataset registration caches require new names after table recreation.
- **Reproducibility:** All SQL, YAML configs, and result CSVs are committed. Experiments can be re-run on any Snowflake account with Cortex Agent access.
